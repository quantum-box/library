PLT-4534 / Design decision / 2026-09-11

Libraryを、外部データの
同期エンジンへ。

GitHub を最初の縦切りとして、CRMや業務SaaSへ広げる。保存・受信・配信をひとつの「同期成功」に丸めず、外部オブジェクトと Library Revision を監査可能に差分交換するための設計です。

判定: Experimental 現行実装には one-shot import までの実用範囲がある一方、継続双方向同期を GA と呼べる durable dispatch・競合処理・状態表示が揃っていません。

01 / Reality map

いま何が動くか

GitHub 連携は単一機能ではなく、別々に追加された複数経路です。経路ごとの保証を分けないと、webhook を受理しただけで「同期済み」に見えるなど、画面と実態がずれます。

usablepartialunsafe / brokentarget
usable

One-shot import

Markdown の一覧、preview、frontmatter mapping、一括 import。同期 binding を作らない独立操作として残します。

境界: import 成功は、その後の継続同期を保証しない。

partial

Outbound writeback

Data 更新 decorator から GitHub Contents API を inline 呼び出し。外部障害が保存経路に混ざり、失敗は warn に留まります。

不足: durable retry / delivery state / 共通 base。

broken in Lambda

Inbound webhook

イベントを DB queue に保存しますが、本番 Lambda では常駐 worker が起動しません。従来は処理されない queue を queued と返せました。

Phase 0: gate 無効時は HTTP 503 を返す。

fragmented

Configuration

ext_github、webhook config、outbound sync config が repo / branch / path / direction を別々に保持します。

結果: 接続の所有者と統一状態を UI が説明できない。

02 / North Star

GitHubは最初のadapter

共通 kernel は binding、外部オブジェクト対応、revision cursor、ChangeSet、delivery、冪等性、retry、conflict、観測性を所有します。provider 固有の識別子とAPI操作は adapter に閉じ込めます。

first slice

GitHub

Markdown file を Library Data と対応。repository / ref / path / commit SHA は GitHub adapter が解釈します。

今回: 危険な現行同期を gate し、共通モデルを定義。

next adapters

CRM

contact / company / deal と Library Data を対応。external ID、ETag、field mapping を provider config として扱います。

同じ経路: inbound review と outbound delivery。

future

業務 SaaS

order、ticket、project などを typed adapter で接続。providerごとのAPI制限やcursorを共通domainへ漏らしません。

共通保証: retry、冪等性、競合、監査。

future

Document / Storage

ファイルや文書を external object として接続。content hash とversionを共通baseに利用します。

削除: providerを問わず tombstone review。

拡張のルールadapter を増やしても Library Record を直接更新しません。すべての外部変更は ExternalChange → InboundChangeSet、すべての外部配信は Library Revision → Transactional Outbox → OutboundDelivery を通ります。

03 / Failure anatomy

「queued」は成功ではない

HTTP 応答が意味できるのは、署名を検証し、後続処理が確実に起動する durable な場所へ保存できたことまでです。consumer が動かない queue への insert は同期の進捗ではありません。

!
最も危険な旧挙動GitHub 側の delete / rename を Data の直接 hard delete / upsert として処理すること。review、CAS、監査がなく、誤削除や force-push を利用者が止められません。

04 / Target flow

安全な差分交換

GitHub の変更は ChangeSet として止め、Library の保存は GitHub 配信から切り離します。両側に独立した revision と状態を持たせることで、競合を黙って上書きしません。

受信の冪等 keybinding + external revision + object ID + change type
配信の冪等 keybinding + library revision + object ID
Delete / rename即時削除せず tombstone を review

05 / Guardrails

守る原則

これは単なる queue の修理ではありません。同期に必要な authority、失敗、競合、利用者判断の境界をプロダクトモデルとして固定します。

01

正本は二つ、勝手に混ぜない

Library accepted revision と GitHub commit SHA は、それぞれの側の truth。共通 base から差分を判定します。

02

保存と配信を分ける

GitHub API が落ちても Library 保存は成功。配信は pending / retrying / failed として後から追えます。

03

外部変更は review を通す

初期 policy は inbound / outbound とも review。自動 accept と direct push は監査 UI が完成するまで導入しません。

04

秘密をコンテンツに入れない

token と webhook secret は Property、ログ、ChangeSet payload に保存せず、tenant-owned connection を binding が参照します。

06 / Domain model

接続とobject対応を分離

repository 単位の外部接続設定と、Data 単位の外部object対応を別 entity にします。利用者が編集する Property を provider cursor の置き場にしません。

proposed

ExternalSyncBinding

  • library_repo_id + provider + connection_id
  • external_scope (typed provider config)
  • object_type + field / content mapping
  • inbound_policy / outbound_policy
  • delete_policy = review_tombstone
  • active / paused / reauthorization_required

接続の所有者、対象範囲、方向、運用状態を repository 単位で一元化。

proposed

ExternalObjectLink

  • binding_id + data_id + external_object_id
  • last_accepted_external_revision
  • last_delivered_library_revision
  • base_content_hash

Library Data と外部objectの対応と、競合判定に必要な共通 base だけを保持。

07 / Migration

段階移行

既存の ext_github を一度に捨てません。互換読み取りと冪等 migration、二重書き parity の確認を経て、最後に legacy field を read-only にします。
