# ADR-0010: 公開ドキュメントの本文と表示構成を分けて管理する

## Status

Proposed (2026-09-07)

PLT-4359。PR #309の閲覧専用UIを起点にした設計提案。トップページと左サイドバーの作り方をレビューするための文書であり、設定API・DB・構成編集UIの実装は含まない。同じPRで、appbarの固定ラベル「利用ガイド」の除去だけを小さな表示修正として扱う。

## Context

PR #309はLibraryのpublic repoをドキュメントとして閲覧する入口を提供した。現在はRepo名・説明と読み込み済みDataの一覧をトップに表示し、左サイドバーも同じ一覧を使う。本文はDataのRichText / Markdown / legacy Htmlから読み取る。

このままでは、読者が最初に何を読むべきか、どの記事が同じテーマに属するかを編集者が指定できない。トップページ用の文章、導入カード、セクション、記事の並びを、本文を複製せず管理したい。

## Decision（提案）

**記事本文は引き続きDataで管理し、トップページとナビゲーションはRepoに属するドキュメント表示設定で組み立てる。** 表示用に別のドキュメント実体を作らない。

### 1. 編集するものを三つに分ける

| 編集対象 | 管理する場所 | 例 |
| --- | --- | --- |
| 記事のタイトル・本文 | Library Data | 「予約を確認する」の手順 |
| トップの紹介文・説明文 | トップ用に選んだDataの本文 | 「TachyonField利用ガイドへようこそ」 |
| セクション・記事順・トップのカード | Repoのドキュメント表示設定 | 「はじめに」に記事を3件並べる |

文章を変えるときは通常のData編集を使う。構成を変えるときはRepo設定の「公開ドキュメント」を使う。記事に専用Propertyを必須追加せず、既存Repoも利用できるようにする。

### 2. ヘッダーとトップページ

appbarはRepo名を既定表示にする。「利用ガイド」など特定用途の固定ラベルは付けない。表示用サイト名を指定した場合だけRepo名を置き換える。パンくずとトップへのリンクも「ガイド」を必須の呼称にせず、Repo名または中立な「トップ」を使う。

設定がないRepoは#309の自動トップ（Repo名・説明・記事一覧）を維持する。

設定があるRepoでは、次の順序で表示する。

1. Repo名、または表示用サイト名。説明もRepoの値を既定とする。
2. 選択した「トップ用Data」の本文。選択しなければ省略する。
3. 選択した「おすすめ記事」のカード。順序と短い紹介文を設定できる。
4. 左サイドバーと同じセクション単位のリンク一覧。

トップ用Dataを指定した場合、トップの大見出しにはそのDataのタイトルを使い、サイト名はヘッダーに残す。カードのタイトルは原則として参照先のData名を使い、二重管理を避ける。紹介文は表示設定で任意指定し、未指定ならタイトルのみ表示する。本文から機械的に先頭文を抜き取らない。

トップ用Dataは通常の記事URLでも読める。自動の「その他の記事」には含めず、必要なら編集者がサイドバーに明示配置する。Dataの更新はトップにも反映される。

### 3. 左サイドバー

最初の段階では、**セクション → 記事の2段階**に限定する。セクションはクリックして記事を開く項目ではなく、折りたためる見出しとする。記事を束ねるだけの空のDataは作らない。

```text
TachyonField 利用ガイド
  トップ

  はじめに
    ようこそ
    クイックスタート
    ワークスペースの基本

  基本操作
    顧客を管理する
    商品・サービスを管理する
    予約を確認する

  設定と管理
    メンバーと権限

  その他の記事
    セクションに未配置の記事
```

- 編集者がセクション名と順序を決め、記事を配置する。
- 同じDataはサイドバー内では1か所にだけ置く。トップのカードからも参照することはできる。
- 開いている記事のセクションは自動で展開する。読者の折りたたみ操作は構成設定を書き換えない。
- 前後の記事リンクは、展開状態に関係なくセクション順・記事順を平坦化して決める。
- サイドバーから漏れたDataは「その他の記事」に表示する。新規記事が意図せず見えなくなる状態を避ける。
- モバイルでは同じ構成を開閉式ナビに表示し、選択後に閉じる。

### 4. 設定の概念モデル

以下は保存する概念の提案であり、既存APIのschemaではない。実装時にRepo設定の保存方式と整合させる。

```json
{
  "version": 1,
  "homeDataId": "data_demo_welcome",
  "featured": [
    { "dataId": "data_demo_quickstart", "description": "最初の操作の流れを確認する" }
  ],
  "sections": [
    {
      "id": "section_demo_start",
      "title": "はじめに",
      "dataIds": ["data_demo_welcome", "data_demo_quickstart"]
    }
  ]
}
```

本文の参照キーはslugではなくData IDにする。記事タイトルを変更しても参照と現行URLが壊れない。セクションIDもタイトル変更・並べ替えで変わらない識別子を用いる。初期段階では任意HTML、外部リンク、クロスRepo参照を設定に入れない。

表示設定はRepoに1件のバージョン付き設定として保存する案を第一候補とする。専用テーブルか既存メタデータの拡張かは、Repoの更新APIと権限モデルの調査後にDDで確定する。本文用Dataに予約JSON Propertyを埋め込む方式は採らない。

### 5. 管理画面の操作

Repo設定に「公開ドキュメント」を設け、次を操作できるようにする。

- トップ用Dataを選ぶ／自動トップに戻す。
- おすすめ記事を追加し、紹介文と順序を編集する。
- セクションを追加・改名・削除し、順序を変える。
- Repo全体から記事を検索してセクションに配置する。
- ドラッグに加えて「上へ」「下へ」「セクションへ移動」を用意し、キーボードでも並べ替えられるようにする。
- 編集中の構成をプレビューし、保存で読者向け表示に反映する。

保存前の構成プレビューは編集権限がある画面内だけで扱い、公開URLに未保存設定を載せない。保存のたびにrevisionを照合し、他の編集者が更新した場合は上書きせず再読み込みを促す。構成編集にはRepo設定を編集する既存の権限を使い、閲覧者やData本文のみを編集できる権限へ自動拡張しない。

セクションの削除は記事削除ではない。記事を未配置に戻し、「その他の記事」で引き続き読めるようにする。

### 6. 公開範囲と壊れた参照

**この設定は表示順を管理するもので、公開権限を管理しない。** public repoのDataは従来どおり公開対象であり、ナビに載せないことを非公開や下書きとして扱わない。非公開化されたRepoでは設定も記事も匿名取得できないことを維持する。

保存時にすべてのData IDが同じRepoに存在することを検証する。重複配置や無効な参照は該当箇所を示して保存を拒否する。保存後にDataが削除された場合は、公開画面でそのリンクを省略し、管理画面では要修正として表示する。トップ用Dataが削除された場合は自動トップに戻す。別Repoのタイトルや本文を参照失敗の説明に含めない。

### 7. 一覧・検索・読み込み

サイドバーの構成は、本文一覧の最初のページだけから作らない。サーバー側でRepo内のDataを検証し、タイトル・ID・順序の軽量なナビゲーションモデルを返す。Data本文は記事を開いたときに個別取得する。

規模が大きい場合はナビモデルの取得上限・ページング方式を実装前に決める。未取得の記事が存在する場合に全記事を表示・検索できたように見せない。タイトル検索はRepo全体を対象にし、検索結果には所属セクションを表示する。本文全文検索は別課題とする。

未配置記事の並びは作成日時とData IDなどの安定したキーで定義し、DBの返却順に依存させない。記事移動後の前後リンクは同じナビrevisionに基づいて計算する。

## Consequences

本文をDataに統一したまま、ドキュメントサイトの入口を編集できる。記事の内容とサイト構成を別々に更新でき、Dataの一般用途へセクション用Propertyを強制しない。一方、Repo表示設定の保存・競合制御・参照検証・ナビモデル取得の追加実装が必要になる。

2段階の構成は運用しやすいが、深い階層を持つAPIリファレンスには不足する可能性がある。最初のTachyonField利用ガイドで運用した後に多段階層を判断する。

## Alternatives Considered

| 案 | 評価 |
| --- | --- |
| Dataにcategory/order Propertyを付ける | 一般的な分類には適するが、空セクション・サイト専用順序・複数の表示構成を表しにくい |
| 全構成をトップDataのJSON本文に書く | 別の保存方式は不要だが、通常の本文編集と構造検証が混ざる |
| GitHubのSUMMARY.mdから構成を同期する | Gitベースの運用には有効だが、Libraryだけで構成を編集したい利用者の入口にならない |
| 独立した記事DBを持つ | 本文・権限・URLが二重管理になるため採らない |
| 任意レイアウトのページビルダーを作る | 自由度は高いが、まず必要なトップ・カード・セクションの操作を大きく超える |

## Follow-up

レビューで確かめたいのは、トップを「Data本文＋おすすめ＋セクション一覧」で十分とするか、左ナビをまず2段階に限定できるか、未配置記事を自動表示してよいかの3点。

合意後にDDで保存モデル・認可・revision更新・ナビAPIの上限とページングを確定し、別の実装PRを作る。受け入れ条件は次のとおり。

- 設定なしの既存public repoが従来のURLで読める。
- Dataの改名・本文更新・削除、セクション移動が一貫して表示される。
- 2ページ目以降の記事も配置・検索・前後移動の対象になる。
- 同時編集を検出し、非公開RepoとクロスRepo参照を漏らさない。
- PC・モバイル・キーボード操作で構成編集と閲覧を確認する。
